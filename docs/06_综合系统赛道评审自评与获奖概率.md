# 综合系统赛道评审自评与获奖概率

## 1. 参赛赛道建议

建议参赛赛道：综合系统赛道。

作品名称：识忆承缘

作品定位：面向人际关系维护场景的可信长期记忆智能体系统。

选择综合系统赛道的原因：

1. 系统具备前端、后端、数据库、缓存、AI 模型调用、Docker 部署和线上访问能力。
2. 系统不是单点算法原型，而是围绕用户登录、人物档案、长期记忆、候选记忆、AI 对话、图片分析、知识库和后台管理形成完整业务闭环。
3. 系统强调工程完整度、业务闭环和可运行性，更符合综合系统赛道对完整软件系统的要求。

不建议主报创新原型赛道的原因：

1. 项目核心优势是系统完整度和应用闭环，不是单一算法突破。
2. 仓颉模块目前作为可插拔规则检测增强层，更适合作为综合系统中的技术亮点，而不是单独支撑创新原型赛道。

## 4. 主要优势

1. 系统闭环完整：用户、人物、记忆、AI 对话、知识库、图片分析和后台管理形成完整流程。
2. 场景明确：围绕“人际关系维护”这一真实需求，避免泛泛而谈的通用聊天。
3. 记忆治理机制突出：AI 抽取出的记忆不直接进入长期记忆库，而是经过候选记忆、人工确认、冲突检测和规则初筛。
4. 工程落地较完整：具备 Docker 部署、线上访问、数据库持久化和接口文档能力。
5. 仓颉模块可作为加分项：以候选记忆规则检测服务形式接入，体现多语言协同和可信治理设计。

## 5. 主要短板

1. 仓颉模块目前是增强模块，不是主流程强依赖，需要在答辩中强调其工程合理性。
2. 自动化测试较少，需要通过测试报告、演示视频和线上运行截图补足可信度。
3. 系统功能较多，答辩时需要突出主线，避免被评委理解成普通 AI 聊天系统。
4. 部署环境依赖 MySQL、Redis 和第三方模型 API，需要提前确保环境变量和服务状态正常。
5. 前端静态资源曾出现容器权限问题，需要在部署文档中说明已修复。

## 6. 答辩定位建议

不要表述为：

> 我做了一个 AI 聊天系统。

建议表述为：

> 我们做的是面向人际关系维护场景的可信长期记忆智能体系统。系统重点解决 AI 长期记忆如何可信进入、如何被用户确认、如何避免冲突和过期的问题。

核心一句话：

> 识忆承缘不是简单聊天，而是围绕人物关系构建“信息采集 - 候选记忆 - 用户确认 - 冲突检测 - 长期记忆调用 - 关系维护建议”的完整智能体闭环。
